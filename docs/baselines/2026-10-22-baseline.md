# NXLYR Baseline 2026-10-22

Oct 22, 2026 · @Vansh Dagar

On build 1e47490 a typical caller turn took 1.4 s server-side, but 9 of 92 turns (10%) stalled 3.2 s waiting for turn release, mostly after one-word replies, which pushed p95 to 4.0 s. The greeting took 3.0 to 4.9 s from pickup, and the logs held the Redis URL, the caller's number and the full prompt on every call.

The 10-call 011 exit test against this baseline runs on 23 Oct.

## Turn-release stall (F07)

9 of 92 caller turns (10%) waited 3.2 s before the bot started its reply, and 8 of those 9 followed a one-word reply. Each stalled turn shows a turn release of 3.200 to 3.203 s while its STT result arrived in 0.34 to 0.46 s, so the wait is Smart Turn's 3 s fallback plus the 0.2 s VAD stop, not slow transcription.

| Script step | Stalls | Calls |
| --- | --: | --- |
| 1. "hello" | 6 | 1, 5, 6, 7, 8, 9 |
| 2. "yes" | 2 | 2, 7 |
| 4. Budget | 1 | 1 |

- The opening "hello" stalled on 6 of 10 calls, so the worst wait lands on the caller's first impression.
- No turn stalled on the long answer with a 0.7 s pause.
- Task 011 (PR #37) releases the turn at whichever comes first: Smart Turn's verdict or 0.8 s after VAD stop, about 1.0 s of silence in all. Replacing each stall with 1.0 s takes p95 from 4,015 ms to about 2,320 ms and the ratio from 2.86 to 1.65, while the median stays at 1,404 ms. Callers would wait 19.8 s less across this batch. These are projections from this data; the 011 exit test measures them.
- The trade-off: a caller who pauses for more than about 1 s mid-thought can now be cut off. The knob is NXLYR\_TURN\_BACKSTOP\_SECS (0.3 to 2.0 s, default 0.8).

## Greeting and tool turns

**Greeting: 3.0 to 4.9 s from pickup, almost all of it before the pipeline's clock starts.** A stopwatch from answering to the bot's first word read 3.0, 3.75, 4.9 and 3.8 s on calls 1, 4, 7 and 10. The greeting's own TTS first audio was only 159 to 300 ms. So roughly 3 s goes on work this log does not time: the knowledge-base fetch, per-call model loads, Redis and service connections, and Exotel's connect. The latency audit names these; task L1 targets them and must add a pickup-to-first-audio log line. The very first call after the container started (before this batch) took 4.3 s for TTS alone, so a fresh deploy's first call is slower still.

**Tool turns: about 0.6 s extra each.** All 19 tool turns (book\_site\_visit 10, transfer\_to\_human 9) made a second LLM call after the tool returned, adding a median 631 ms. The tools themselves took 3 to 10 ms. These turns sit at 2.1 to 2.5 s and become the slowest turns once 011 removes the stall. Task 008 (truthful tools) and prompt v2 own this.

**LLM first token is the largest steady cost** at a 726 ms median, with rare spikes to 1.8 and 2.4 s. It is a candidate for a later experiment (prompt size, model), not a pre-outreach fix.

## What the caller heard

The bot sounded scripted and once invented the caller's name, which costs more trust than the latency does. These are the founder's by-ear notes; every cause below is a hypothesis until checked.

| What was heard | How often | Likely cause (unverified) | Where it gets fixed |
| --- | --- | --- | --- |
| "Fair question" before replies; almost every line ends in a question | Most turns | agent/bot.py holds a sample exchange answering "This sounds expensive" with "Fair question. ... Want me to send over the full breakdown?"; if those samples reach the prompt, the model copies them | Prompt v2 |
| "Sure!", "I appreciate you sharing your budget", the same facts repeated, long preachy sentences, a hand-holding monotone | Most calls; call 9 worst | Prompt style rules | Prompt v2 |
| Called the caller "Daniel" | Once | The lead's name is not passed in, so the model invents one | Name plumbing, prompt v2 |
| A second greeting after the caller says hello | Whenever the caller greets | The static greeting plays, then the model greets again | Prompt v2 or context fix |
| First words snappy, the rest of the same sentence sluggish | 9 of 10 calls | Either the voice and model's pacing on long sentences, or audio reaching the call slower than it plays. Nothing in the logs measures past the first audio | Listening test, then L3 |
| Bot keeps talking 0.5 to 1 s after the caller cuts in | Every interruption | Audio already buffered toward Exotel plays out | New item; needs research |
| Amounts misheard: Rs, thousand, twelve | Calls 2, 3, 4, 6 | STT on Indian number words | New item: STT options A/B |
| Stopped speaking for background noise | Once (call 2) | VAD | Watch only |
| Uneven tone: some words natural, others thrown out | Several calls | Sentence-by-sentence TTS loses context between requests | L3 TTS test |

The listening test that splits the sluggish-sentence causes takes ten minutes: paste two of the bot's long sentences into the ElevenLabs web app with the live voice and Flash v2.5. If the second half drags there too, it is the voice and model; if not, it is our pipeline.

## Caveats and open questions

- One tester, one phone, one quiet room, one accent, scripted lines. Real leads will pause, mumble and speak Hinglish; this batch says nothing about those.
- Sum of stages is server-side. Telephony, network and the caller's handset add time the logs cannot see.
- The latency CSV is a weaker source than the events log: it has no call id, its turn column is a running counter across calls, and it appears to lag one row (it held the earlier call's last turn and missed call 10's last turn). Use the events log.
- Both files live inside the container and are deleted on every deploy or recreate. Copy them off before merging anything.
- Open: is the sluggish second half of a sentence the voice or our pipeline? (listening test)
- Open: can Exotel be told to drop buffered audio when the caller interrupts?
- Open: which knowledge-base, model or connection step makes up the roughly 3 s before the greeting? (L1 logging)

## How to reproduce

Run every step in one terminal tab on the founder's Mac, so T0 and BEFORE survive. Raw files for this batch are in `/Users/vansh/Desktop/SALES AGENT/baseline-2026-10-22/`: baseline-events.log, baseline-raw.csv and notes.md. Both scripts live in `/Users/vansh/Desktop/SALES AGENT/tools/`.

1. Raise the demo limits for the batch:

```
ssh nxlyr-vps "docker exec nxlyr_redis redis-cli HSET demo:config phone_limit 100 ip_limit 100 phone_cooldown_seconds 5 ip_cooldown_seconds 5"
```

2. Mark the start:

```
T0=$(date -u +%Y-%m-%dT%H:%M:%SZ); echo "$T0"
```

3. Place 10 calls with the script above, one at a time, 10 s apart. Note by ear per call, and time the greeting by stopwatch on calls 1, 4, 7 and 10.
4. Copy the files off and check them for phone numbers (both counts must be 0):

```
ssh nxlyr-vps "docker cp nxlyr_agent:/app/section6_real_call.csv /tmp/ && docker cp nxlyr_agent:/app/section6_real_call_events.log /tmp/"
scp nxlyr-vps:/tmp/section6_real_call_events.log ./events.log
scp nxlyr-vps:/tmp/section6_real_call.csv ./raw.csv
grep -cE '[0-9]{10}' ./events.log ./raw.csv
ssh nxlyr-vps "rm -f /tmp/section6_real_call.csv /tmp/section6_real_call_events.log"
```

5. Report (latency\_report.py v3). Use --from-call to drop calls made before the batch; after a fresh deploy, use 0:

```
python3 latency_report.py ./events.log --from-call 0 --md
```

6. Log-leak counts. The script asks for the last six digits of the test phone; run it on its own line:

```
./leak_counts.sh "$T0"
```

7. Restore the demo limits; both reads must be empty:

```
ssh nxlyr-vps "docker exec nxlyr_redis redis-cli DEL demo:config"
ssh nxlyr-vps "docker exec nxlyr_redis redis-cli HGETALL demo:config"
ssh nxlyr-vps "docker exec nxlyr_redis redis-cli GET demo:kill"
```
