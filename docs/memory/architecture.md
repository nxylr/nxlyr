# Architecture (verified facts only — mark anything else `UNVERIFIED:`)

## Call flow
1. Visitor submits demo form (dashboard, Vercel) → `POST /demo/call` on `api.infrasmith.dev` (nginx → agent container).
2. Server dials via Exotel Connect API (Basic auth). On a real Call SID it writes `ws_bind:<call_sid>` to Redis (`{"issued_at": <ts>}`, 120s TTL). Exotel then opens `wss://api.infrasmith.dev/ws`.
3. `/ws` (`agent/server.py`, `agent/ws_auth.py`): accept → read the handshake (`connected`/`start`, 5s timeout, 16 KiB limit) → `GETDEL ws_bind:<call_sid>` (polled up to ~3s, 1s Redis timeouts) → in-process admission counter (`MAX_CONCURRENT_WS`, default 10) → `run_bot` with the consumed frames replayed. The Exotel Call SID equals the start-message `call_sid` (verified on one real call, 2026-10-13).
   - `WS_AUTH_MODE=log|enforce`, code default `log`. Enforce closes with 1008 before any pipeline object is built and fails closed if Redis is unavailable. Log mode never rejects: it logs `ws_auth would_reject reason=…` and continues; an unbound call is held ~3s by the poll. The mode is read per connection from the environment.
   - `scripts/ws_probe.py` is an anonymous probe (no secrets) that prints the close code.
4. `agent/bot.py` runs the Pipecat pipeline: Silero VAD with VAD and transcription turn-start strategies → Deepgram STT → GPT-4o → ElevenLabs (HTTP TTS).
   - Turn release (task 011, PR #37): Smart Turn v3 decides first, with a speech-timeout backstop; Silero VAD stop is 0.2 s (pipecat default). `NXLYR_TURN_MODE` (`smart_backstop` default, or `speech_timeout`) and `NXLYR_TURN_BACKSTOP_SECS` (0.3 to 2.0, default 0.8) are validated at import, so a bad value stops the container at start. The live mode line is `turn release configured: mode=… backstop_secs=…`.
   - Logging (task 004, PR #38): `agent/log_scrub.py` installs one loguru handler with `diagnose` off, drops `pipecat.services.openai.base_llm` DEBUG lines, masks phones to the last 4 digits, and removes secret env values and token shapes. `LOG_LEVEL` defaults to DEBUG in code and is unset in the VPS `.env`, so production logs at DEBUG until the founder sets INFO (founder-reported; set it unset, never empty: an empty value crashes boot). uvicorn's own lines are not scrubbed.
   - Measurement: `section6_real_call_events.log` is the primary latency source; both latency files live in the container and are lost on every deploy, so copy them off before deploying.
   - Start-up timing (task 015, PR #42): loguru lines `call timing: <event> conn=<6 hex> t_ms=<ms since ws_connected>` (events `ws_connected`, `models_built`, `setup_done` with `kb_ms`, `kb_source`, `redis_ms`, `handshake_ms`, `greeting_queued`, `first_bot_audio_sent`, `caller_spoke_before_greeting_audio`). They are in `docker logs nxlyr_agent`, not `events.log`. `conn` is random, not the call SID.
   - Pickup to first word (founder stopwatch, 3 silent calls, 2026-10-24, after 015): 3.89 to 4.3 s. Our server (`ws_connected` to `first_bot_audio_sent`) is 0.5 to 1.2 s (457 to 1,168 ms); Exotel and the phone network account for the other 3.1 to 3.4 s, by subtraction, split unmeasured. A server in India does not remove that part, because the bridging happens before the call reaches us (see inbox).
   - Per-call switches in Redis, read once at call start, no deploy needed (tasks 018, 019). Code defaults are what a call gets when a hash is absent, a field is invalid or Redis is slow (WARNING, never a broken call); `DEL <key>` reverts.
     - `convo:config` (hash, `agent/convo_config.py`, 0.5 s read): `prompt_version` v2|v21 (default v2), `stt_keyterms` on|off (off), `stt_numerals` on|off (off), `stt_region` global|eu (global), `greeting_tags` on|off (off; v4 only, otherwise the plain greeting is used and the log says `blocked`). One `convo config:` log line per call.
     - `voice:config` (hash, `agent/voice_config.py`): per field, valid Redis value > environment variable (`ELEVENLABS_*`, `TTS_PROVIDER`) > code default. Fields: model, voice, stability, similarity_boost, style, use_speaker_boost, speed, optimize_streaming_latency, keepwarm_seconds (0 or 60 to 3600, default 240). For `eleven_v4*` only stability and similarity_boost are sent; the log line lists `dropped=`. Bracketed tags are stripped for non-v4 models.
   - Deepgram (task 018): `STTCheckingDeepgramService` in `agent/stt_keyterms.py` adds KB key terms (project name, developer, city, sector, fixed terms), logs `stt endpoint: … host=` (`api.eu.deepgram.com` when `stt_region=eu`, with a WARNING on a mismatch) and a sanitised `stt check:` line per final transcript. **The class name must contain "STT"**: `tools/latency_report.py` matches `"STT"` case-sensitively in the Pipecat service name for its "STT first result" row; a rename drops the row.
   - ElevenLabs keep-warm (task 019, `server.py` `_keep_voice_warm_forever`): a small TTS request at startup and every `keepwarm_seconds`; logs `voice keep-warm: ok model=… ttfb_ms=…` or a `failed` line. Per the founder it is running; how long a warm voice stays warm and what the requests cost in characters are not measured.
5. Tools in `agent/tools.py` (`book_site_visit`, `transfer_to_human`, `end_call`) still write flags to a Redis session hash (4h TTL). Since task 008 (PR #46) a booking or callback request also goes through `agent/commitments.py`:
   - A `call_commitments` row is inserted (Supabase REST, service role), then a Telegram alert is sent, then `alert_sent_at` is set. **The tool reports success only after both**; any failure, timeout or refusal is a fixed sentence spoken by code (`TTSSpeakFrame`, `run_llm=False`), so the model cannot improvise a promise. Success turns still make a second LLM call.
   - The commit, marker, supersede and Redis flags run in one retained background task per tool call; the result is published as soon as the alert succeeds, and a hang-up cannot cancel the rest. Caps: store 3 s, alert 3 s, commit 6 s (lookup, insert, alert).
   - Visits are validated in IST: 09:00 to 19:00, within 90 days, not in the past. A later booking on the same call sets `superseded_at` on the earlier row (kept) and sends an "Updated booking" alert. A retry of the same booking updates its row (unique `call_sid, kind, visit_date, visit_time`).
   - The lead's phone is the party that is not our `EXOTEL_PHONE_NUMBER`; null if unclear. No model or caller free text is logged by tools; `log_scrub.py` also drops Pipecat's DEBUG "Calling function … with arguments" line.
6. `agent/kb_loader.py` loads `projects.config` from Supabase. Since 015 the KB is preloaded in `lifespan` (`asyncio.to_thread`) and refreshed every 240 s (`KB_REFRESH_INTERVAL_SECONDS`) by a background task; the call path serves the cache whatever its age and fetches only on an empty cache, in a worker thread. A failed preload logs an error and does not stop startup. Fetch timeout is (2.0, 5.0) s. A stale entry logs `Serving stale KB cache_age_seconds=…` (WARNING) while `setup_done` still says `kb_source=cache`. Known debts: a single refresh has no overall deadline, and nothing alerts when the KB goes stale.

## Infra
- Hetzner VPS, `/opt/nxlyr`, docker compose, nginx at `api.infrasmith.dev`. Redis in a container.
- Repo copy of `docker-compose.yml`: agent and redis publish on `127.0.0.1` only; both read `env_file: /mnt/secrets/.env`. A local `docker-compose.override.yml` (gitignored) repoints env_file for laptops.
- Repo copy of `infra/nginx/api.infrasmith.dev.conf` (not necessarily what is live): proxies `/ws` (prefix), `/demo/call` (prefix, CORS for `https://nxlyr.vercel.app`) and `= /contact` to `127.0.0.1:7860`. Everything else, including `/start` and `/health`, falls to static `location /` → 404. So `/health` returns an nginx 404 externally (observed by the human too); the container healthcheck hits it on loopback. The real gate is a real call.
- Frontend: Next.js in `dashboard/`, Vercel production follows `main`.
- CI/CD: `.github/workflows/deploy.yml` — on push to `main`: SSH → `cd /opt/nxlyr && git pull origin main && docker compose up -d --build`. No path filter: every push to `main`, including a docs-only merge, runs the SSH step (checked in the workflow file on 2026-10-24), so every merge is a redeploy attempt. A docs-only merge does rebuild the image and recreate the container (observed on the PR #41 deploy: `nxlyr_agent` went from created 2026-10-23T14:26:47Z, image `sha256:c151a724…`, up 21 hours, to created 2026-10-24T11:41:28Z, image `sha256:92719f19…`, up 19 seconds healthy; `nxlyr_redis` stayed up 10 days). UNVERIFIED: why a docs-only change alters the image (probably `docs/` is in the build context). A path filter is in the inbox. No concurrency control. Build runs an `import server` smoke. No workflow runs the unit tests; `lint.yml` checks `api/` (empty) and always passes.
- Local runs: `agent/venv` exists only in the main checkout (gitignored); see AGENTS.md "Commands".

## Supabase tables (live)
tenants (has `api_key` — never SELECT *), projects (`config` jsonb = KB), leads (unique project_id + phone_normalized), calls (`exotel_call_id` unique, lead_id/tenant_id NOT NULL), call_events (payload jsonb), transcripts (one row per call: content, turns jsonb, word_count), qualifications (unique per lead), analytics_daily, voice_clones, contact_submissions, commitments, consents, call_commitments (008: `kind` site_visit|callback_request, `alert_sent_at`, `superseded_at`; RLS on, no policies; service role bypasses).
